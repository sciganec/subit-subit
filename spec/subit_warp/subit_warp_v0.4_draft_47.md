## 1. Призначення аудиту

W46 оцінює готовність SUBIT-WARP v0.4 до переходу зі статусу DRAFT у STABLE.

Це не повторення попередніх математичних аудитів. Завдання документа — перевірити, чи утворюють попередні результати достатню, несуперечливу та відтворювану основу для релізу.

Аудит розділяє п'ять різних рівнів готовності:

1. **Mathematical validity** — математична коректність означень, тверджень і виведень.
2. **Proof completeness** — наявність повних доказів для тверджень, які мають статус доведених.
3. **Formalization readiness** — можливість однозначно перенести математичні конструкції у формальну мову.
4. **Implementation and test readiness** — наявність реалізації, тестів та відтворюваних результатів.
5. **Release integrity** — узгодженість версій, походження тверджень, контроль залежностей та документації.

Ці рівні не є взаємозамінними.

Текстовий доказ не є Lean-перевіркою.  
Lean Blueprint не є Lean-реалізацією.  
Наявність тестових вимог не означає виконання тестів.  
Математична узгодженість окремого модуля не доводить узгодженість усієї архітектури.

Основне правило W46:

**DO NOT COLLAPSE — CONTEXTUALIZE.**

## 2. Критерії оцінювання

Для кожного компонента застосовується одна з п'яти категорій.

- **ACCEPTED** — вимога достатньо обґрунтована в межах доступного матеріалу.
- **CONDITIONALLY ACCEPTED** — результат прийнятний за явно визначених передумов.
- **OPEN** — питання ще не закрите.
- **BLOCKED** — відсутність необхідного джерела, доказу або реалізації перешкоджає наступному етапу.

**RELEASE-BLOCKING** — невирішена проблема, яка не дозволяє оголосити v0.4 стабільною.

**NON-BLOCKING** — покращення, яке не впливає на математичну чи технічну коректність заявленого обсягу релізу.

## 3. Аудит математичного ядра

### 3.1. Адресний простір

Зафіксована модель:

- b ≥ 2;
- B_b = {1, …, b};
- Pos_b = B_b^{<ω};
- Σ_b = B_b^ℕ.

Адреси є скінченними словами над B_b, а нескінченні гілки — нескінченними послідовностями елементів B_b.

**Оцінка: ACCEPTED.**

Ця конструкція математично стандартна та придатна для формалізації.

Однак у формальній реалізації b має бути параметром, для якого явно доступний доказ 2 ≤ b. Необхідно уникнути ситуації, коли частина модулів працює з довільним b, а інша — лише з b ≥ 2.

### 3.2. Простір кодів

Код:

S_A = {ABSENT, INTERNAL} ∪ {LEAF(a) : a ∈ A}

RawCode:

Code_b(A) = S_A^{Pos_b}.

Визначені умови локальної допустимості, зокрема закриття для ABSENT та LEAF.

**Оцінка: CONDITIONALLY ACCEPTED.**

Для релізу необхідно забезпечити єдине джерело істини щодо таких правил:

- чи може корінь бути ABSENT;
- чи може LEAF мати нащадків;
- чи означає ABSENT відсутність вузла, а не невідомість;
- чи є INTERNAL вузол із усіма b дочірніми позиціями;
- які саме умови роблять код rooted.

Особливо важливо не змішувати:

**ABSENT ≠ UNKNOWN.**

ABSENT — структурна відсутність позиції. UNKNOWN — епістемічна невизначеність щодо інформації.

Ці стани можуть мати різні значення в різних шарах системи, але не повинні зливатися в одному базовому типі.

### 3.3. Повні та часткові дерева

Архітектура розрізняє:

- C_Partial^all — локально допустимі коди;
- C_Partial — rooted partial codes;
- C_Full — rooted codes, у яких кожен INTERNAL має всі b наявних дочірніх позицій.

**Оцінка: CONDITIONALLY ACCEPTED.**

Потрібна остаточна перевірка, що всі визначення використовують однакові правила rootedness та closure.

Необхідно зберегти різницю між локальною структурною повнотою та існуванням нескінченного продовження.

### 3.4. Умова нескінченного продовження

Визначення:

IB(u,t) ⇔ t(u) = INTERNAL ∧ існує нескінченна гілка, що продовжує u і проходить лише через INTERNAL-вузли.

Тоді:

Tω_P = {t ∈ C_Partial : ∀u, t(u) = INTERNAL ⇒ IB(u,t)}.

Tω_P⁺ = {t ∈ Tω_P : t(ε) = INTERNAL}.

**Оцінка: CONDITIONALLY ACCEPTED.**

Математичний задум визначений, але формалізація потребує точної конструкції продовження адреси.

Рекомендоване визначення для Lean Blueprint:

Нехай u — скінченна адреса, а η : ℕ → Fin b — нескінченний хвіст.

Визначимо:

extendAddress(u, η, n) = u ++ η.take(n).

Тоді:

IB(u,t) ⇔ t(u) = INTERNAL ∧  
∃η : ℕ → Fin b, ∀n ≥ 0,  
t(u ++ η.take(n)) = INTERNAL.

Це усуває неоднозначність між повною адресою ξ та її продовженням від довільного вузла u.

Окремо слід зберегти важливий крайовий випадок:

Rooted LEAF tree може належати Tω_P, оскільки умова для INTERNAL-вузлів виконується вакуумно.

Але:

Rooted LEAF tree ∉ Tω_P⁺.

Скінченне rooted tree, яке містить хоча б один INTERNAL-вузол без нескінченного INTERNAL-продовження, не належить Tω_P.

Це уточнення має бути перенесене до регресійної специфікації.

## 4. Аудит метрики та граничного відображення

### 4.1. Кодова метрика

Визначена метрика:

d_code(t,s) = 2^(−r_code(t,s)),

де r_code — мінімальна глибина адреси, на якій коди відрізняються.

Для однакових кодів r_code = ∞ та d_code(t,t) = 0.

**Оцінка: ACCEPTED на математичному рівні.**

Необхідно зберегти одну канонічну назву метрики.

W39.1 правильно рекомендує використовувати restriction d_code на підпросторах замість невизначеної d_P.

Історичну d_F не можна автоматично ототожнювати з d_code без прямого джерельного підтвердження.

### 4.2. Boundary map

Визначення:

∂t = {ξ ∈ Σ_b : ∀k ≥ 0, t(ξ|k) = INTERNAL}.

Домен:

Tω_P⁺ = {t ∈ Tω_P : t(ε) = INTERNAL}.

Для цього домену межа непорожня, замкнена та компактна.

**Оцінка: CONDITIONALLY ACCEPTED.**

W41 надає текстове закриття T-007.

Однак перед релізом потрібно:

1. перевірити, що всі попередні означення boundary map використовують той самий домен;
2. перевірити, що нескінченна гілка справді складається лише з INTERNAL-вузлів;
3. перевірити, що compactness theorem застосовується до правильно визначеного простору;
4. формально зафіксувати залежність від компактності Σ_b.

### 4.3. Lipschitz-оцінка

Заявлено:

d_H,Σ(∂f,∂g) ≤ 2d_code(f,g).

**Оцінка: CONDITIONALLY ACCEPTED.**

Аргумент W41 використовує першу глибину розходження m та факт, що для rooted INTERNAL trees m ≥ 1.

Однак окремо необхідно закрити заяву про оптимальність константи 2.

Для цього потрібно побудувати явну пару дерев.

Нехай u — адреса довжини m−1. Виберемо два різні символи i ≠ j.

У дереві f нескінченне INTERNAL-продовження після u існує лише через дочірню позицію i.

У дереві g — лише через дочірню позицію j.

Водночас усі координати на глибинах менших за m мають збігатися.

Тоді:

d_code(f,g) = 2^(−m),

d_H,Σ(∂f,∂g) = 2^(−(m−1)),

отже:

d_H,Σ(∂f,∂g) = 2d_code(f,g).

Але ця конструкція ще має бути перевірена щодо всіх умов Tω_P: кожен INTERNAL-вузол обох дерев повинен мати нескінченне INTERNAL-продовження.

До завершення цієї перевірки константу 2 можна використовувати як доведену верхню оцінку в межах W41, але її глобальну оптимальність слід позначати як OPEN.

**Релізний статус:** RELEASE-RELEVANT.

## 5. Аудит спектральної теорії

W42 розглядає оператори, визначені ядрами на Σ_b.

Простір:

H = L²(Σ_b, μ_b).

Циліндричні підпростори:

H = H₀ ⊕ ⨁_{j≥1} W_j,

де:

dim W_j = (b−1)b^(j−1).

### 5.1. Спадне ядро

K_q(ξ,η) = q^{ℓ(ξ,η)}, 0 ≤ q ≤ 1.

Заявлені власні значення:

λ₀(q) = (b−1)/(b−q),

λ_j(q) = −(1−q)q^(j−1) / [b^(j−1)(b−q)].

Кратність:

m_j = (b−1)b^(j−1).

**Оцінка: CONDITIONALLY ACCEPTED.**

W42 містить аналітичний спектральний розрахунок, але його повна сумісність із попереднім канонічним означенням оператора W30 не підтверджена.

Необхідно перевірити:

- точне означення ℓ(ξ,η);
- нормалізацію міри;
- інтегральну форму оператора;
- граничні випадки q = 0 та q = 1;
- відповідність власних підпросторів обраній циліндричній фільтрації.

### 5.2. Зростаюче ядро

K_t(ξ,η) = t^{ℓ(ξ,η)}, t > 1.

W42 отримує:

- boundedness при 1 < t < b;
- compactness при 1 < t < b;
- Hilbert–Schmidt condition t² < b;
- відсутність trace-class властивості для t > 1;
- відсутність обмеженого оператора, що реалізує задану інтегральну форму на всьому L², при t ≥ b.

**Оцінка: CONDITIONALLY ACCEPTED.**

Особливо важливо не змішувати три різні твердження:

1. Існування обмеженого оператора.
2. Існування компактного оператора.
3. Існування trace-class оператора.

Це різні класи операторів із різними критеріями.

Для t ≥ b формулювання має бути точним: розбіжність квадратичних форм на константній функції свідчить про неможливість обмеженого оператора, який реалізує саме цю інтегральну форму на всьому L² за прийнятої нормалізації.

Не слід робити ширші твердження про всі можливі операторні продовження без окремого доказу.

### 5.3. Скінченні апроксимації

W42 наводить матричні компресії:

T_q^(n) = P_n T_q P_n | H_n.

Також наведено trace-norm convergence:

‖T_q − P_nT_qP_n‖₁ = (b−1)/(b−q) · q^n, 0 ≤ q < 1.

**Оцінка: CONDITIONALLY ACCEPTED.**

Перед релізом потрібна перевірка відповідності матричних формул і нормування базису точному означенню оператора W30.

## 6. Encoding / Decoding: критичний пробіл

У доступному контексті є архітектура W39 та формалізаційний план W45, але немає повного первинного тексту W43.

Тому W46 не може підтвердити, що W43 повністю закрив такі властивості:

1. Decode(Encode(x)) = x.
2. Encode(Decode(t)) = t.
3. Збереження constructor structure.
4. Збереження rootedness.
5. Збереження ABSENT та LEAF closure.
6. Збереження нескінченних INTERNAL-продовжень.
7. Узгодженість структурної та адресної репрезентацій.
8. Bisimulation або еквівалентний принцип coinductive reconstruction.

**Оцінка: BLOCKED.**

Це RELEASE-BLOCKING.

До отримання та перевірки повного W43 не можна вважати encoding/decoding шар завершеним.

Важливо: W45 описує бажану архітектуру формалізації, але не замінює доказів round-trip properties.

## 7. Lean 4 readiness audit

W45 створив архітектуру модулів та перелік proof obligations.

Це корисний формалізаційний blueprint, але не готова реалізація.

### 7.1. Критичні уточнення

Необхідно:

- замінити неоднозначну конструкцію HasInfiniteContinuation на точне визначення через нескінченний хвіст;
- уніфікувати параметр b та доказ 2 ≤ b;
- визначити метрику без неоднозначного використання нескінченного показника;
- перевірити типи всіх subtype projections;
- відокремити inductive finite structures від справжніх coinductive або address-indexed infinite structures;
- визначити точні типи для boundary, compactness та Hausdorff distance;
- зафіксувати політику щодо axioms, sorry та admitted theorems.

### 7.2. Рекомендована стратегія

Перший етап Lean-реалізації має використовувати address-indexed representation.

Це дозволить формально визначити:

- RawCode;
- PartialCode;
- FullCode;
- Rooted;
- InfiniteContinuation;
- OmegaPartial;
- OmegaPartialPlus.

Лише після перевірки цих структур слід переходити до альтернативної coinductive representation.

### 7.3. Статус

**FORMALIZATION READINESS: PARTIAL.**

**LEAN COMPILATION: NOT VERIFIED.**

**KERNEL VERIFICATION: NOT PERFORMED.**

Це RELEASE-BLOCKING для будь-якого релізу, який заявляє Lean-verified результати.

Якщо v0.4 буде позиціонуватися як математична специфікація без формальної верифікації, Lean може залишитися явно позначеним майбутнім етапом. Але тоді реліз не повинен містити тверджень про kernel-verified proofs.

## 8. Регресійний аудит W44

W44 визначає 39 регресійних вимог R1–R9.

Це достатня основа для побудови тестового плану, але не свідчення фактичного виконання тестів.

Окремо необхідно зберегти уточнення W44-R020:

- rooted LEAF tree належить Tω_P;
- rooted LEAF tree не належить Tω_P⁺;
- скінченне rooted tree з INTERNAL-вузлом не належить Tω_P, якщо цей вузол не має нескінченного INTERNAL-продовження.

**Оцінка: CONDITIONALLY ACCEPTED.**

Відсутність виконаних тестів не спростовує математичної моделі, але не дозволяє заявляти про regression-tested implementation.

Перед релізом потрібні:

1. формалізація регресійних вимог як машинно перевірюваних тестів;
2. позитивні та негативні приклади;
3. тести крайових випадків;
4. тести round-trip encoding/decoding;
5. перевірки boundary map;
6. перевірки спектральних апроксимацій;
7. окремий звіт про результати виконання.

**AUTOMATED TEST EXECUTION: NOT VERIFIED.**

## 9. Source provenance audit

Найважливіший ризик для цілісності релізу — неповна перевірка історичних джерел.

У межах доступного матеріалу не завершено пряме звірення:

- W20 — історичні регресійні вимоги;
- W30 — первинне означення спектрального оператора;
- W23′ — попередні математичні конструкції;
- W43 — повний текст encoding/decoding audit.

Тому відповідність W39–W45 цим документам залишається частково умовною.

### 9.1. Правило provenance

Кожне твердження, яке переходить у канонічну специфікацію, повинно мати:

- identifier;
- точне формулювання;
- джерело;
- статус доказу;
- залежності;
- відомі обмеження;
- відповідний тест або formal theorem, якщо застосовно.

### 9.2. Заборона мовчазного успадкування

Якщо новий документ змінює означення, він повинен явно вказати:

- що саме змінено;
- яке попереднє означення замінено;
- чи є зміна сумісною;
- які теореми залежать від старої версії;
- чи потрібно повторно перевірити докази.

**Оцінка: BLOCKED.**

Прямий source cross-check є RELEASE-BLOCKING для твердження про повну історичну сумісність v0.4.
