# SUBIT-ECOSYSTEM MASTER TECHNICAL SPECIFICATION v0.1.0

## Інкремент 02: SUBIT-CORE CONTRACT REGISTRY &amp; VERSION COMPATIBILITY POLICY v0.1.0

(SPECIFICATION DRAFT) (Архітектурний рівень) (Наступний логічний інкремент)

**Статус\:** проєкт нормативної специфікації
**Призначення\:** Master Technical Specification v0.1.0
**Область\:** SUBIT-CORE, міжмодульні контракти, канонічні структури даних, версіонування та сумісність.

Цей інкремент продовжує роботу над міжмодульною архітектурою SUBIT-ECOSYSTEM. Попереднім кроком було визначення типів залежностей і матриці взаємодії модулів. Тепер необхідно закріпити механізм, який дозволить цим модулям взаємодіяти без прихованих припущень щодо структури даних, семантики повідомлень і версій.

**Головне архітектурне рішення\:** жоден модуль SUBIT-ECOSYSTEM не повинен самостійно визначати значення чужих даних або припускати сумісність чужого інтерфейсу. Кожна взаємодія має спиратися на явно зареєстрований контракт, контекст і походження даних.

---

# 1\. Мета інкременту

SUBIT-ECOSYSTEM складається з модулів, які мають різні функції\:

- SUBIT-CORE визначає базові типи та інваріанти.
- SUBIT-LANG інтерпретує та формалізує команди.
- SUBIT-DATA зберігає події й забезпечує відтворення стану.
- SUBIT-RUNTIME координує виконання.
- SUBIT-CPU виконує формалізовані операції.
- SUBIT-AI формує інтелектуальні пропозиції та висновки.
- SUBIT-TOOLS взаємодіє із зовнішніми інструментами.
- SUBIT-VERIFICATION перевіряє відповідність контрактам та інваріантам.

Без централізованої системи контрактів виникають типові проблеми\:

1. Модулі по-різному трактують однакові поля.
2. Оновлення одного модуля непомітно порушує інший.
3. Дані втрачають контекст під час передавання.
4. Походження результату стає невідомим.
5. Події неможливо надійно відтворити.
6. Різні версії модулів можуть взаємодіяти з несумісними припущеннями.
7. Валідація перетворюється на набір розрізнених перевірок.

Тому вводиться **SUBIT Contract Registry (SCR)** — централізований реєстр контрактів, який визначає допустимі структури, версії, залежності, семантичні обмеження та правила сумісності.

SCR не є новим незалежним джерелом істини про сутності або події. Він є реєстром нормативних правил їх взаємодії.

## 1.1. Основний результат

Після цього інкременту специфікація повинна визначати\:

- канонічний формат контракту;
- формат маніфесту модуля;
- розмежування Entity, Event, Context і Provenance;
- формат Event Envelope;
- правила версіонування;
- алгоритм перевірки сумісності;
- політику обробки невідомих полів і типів;
- вимоги до інтеграції восьми базових модулів;
- критерії прийняття контракту.

# 2\. Архітектурна позиція

## 2.1. DO NOT COLLAPSE — CONTEXTUALIZE

Цей принцип стає обов'язковою вимогою до всіх контрактів.

Два значення, які мають однакове представлення, не обов'язково мають однакову семантику.

Наприклад\:

- `10` у координаті WHO означає ME;
- `10` у координаті WHERE означає EAST;
- `10` у координаті WHEN означає SPRING;
- `10` у системі Belnap/Dunn FOUR означає T.

Ці значення не можна ототожнювати тільки через однакову бітову форму.

Тому контракт повинен визначати не лише значення, а й його тип, простір інтерпретації та контекст.

Формально\:

`Value = (Representation, Type, Context, Provenance)`

Семантична тотожність\:

`x ≡ y`

допускається лише за сумісності типу, семантики та відповідного контексту.

Рівність бітового представлення\:

`bits(x) = bits(y)`

сама по собі не є достатньою умовою семантичної тотожності.

## 2.2. Типова ізоляція FOUR та SUBIT-64

Уводяться два незалежні типи\:

```
SubitState64:
    who: WHO
    where: WHERE
    when: WHEN

BelnapValue:
    N = 00
    F = 01
    T = 10
    B = 11
```



Забороняється неявне перетворення\:

```
SubitState64 -> BelnapValue
BelnapValue -> SubitState64
```



Якщо певна операція потребує такого відображення, вона повинна мати окремий контракт перетворення з явною семантикою.

Це правило поширюється на всі модулі, включно з CPU, AI, LANG та VERIFICATION.

# 3\. SUBIT Contract Registry

## 3.1. Призначення

SCR є нормативним реєстром, у якому кожен контракт має\:

- унікальну ідентичність;
- власника;
- версію;
- тип;
- структуру;
- семантичний опис;
- передумови;
- постумови;
- інваріанти;
- правила сумісності;
- статус життєвого циклу.

Реєстр має бути логічно відокремлений від конкретної реалізації модулів.

Модуль може реалізувати контракт, але не може одноосібно змінити його нормативний зміст.

## 3.2. Канонічна структура Contract

```
Contract:
    contract_id
    contract_version
    owner_module
    contract_kind
    semantic_domain

    input_schema
    output_schema

    preconditions[]
    postconditions[]
    invariants[]

    compatibility_policy
    dependencies[]

    lifecycle:
        status
        introduced_in
        deprecated_in
        sunset_at

    documentation_ref
    conformance_profile
```



### Пояснення полів

`contract_id` — стабільний ідентифікатор контракту.

`contract_version` — версія його публічного інтерфейсу.

`owner_module` — модуль, відповідальний за нормативне визначення контракту.

`contract_kind` — тип контракту\:

- ENTITY\_SCHEMA;
- EVENT\_SCHEMA;
- COMMAND;
- QUERY;
- RESULT;
- TRANSFORMATION;
- ADAPTER;
- CAPABILITY;
- VERIFICATION\_RULE.

`semantic_domain` — область значень, у якій інтерпретується контракт.

`input_schema` та `output_schema` — структурні вимоги.

`preconditions` — умови, необхідні перед виконанням.

`postconditions` — умови, які мають бути виконані після завершення.

`invariants` — умови, які повинні залишатися істинними протягом життєвого циклу.

`compatibility_policy` — правила сумісності версій.

`dependencies` — перелік інших контрактів, без яких цей контракт не може функціонувати.

## 3.3. Статуси контракту

Вводиться п'ять статусів\:

```
DRAFT
EXPERIMENTAL
STABLE
DEPRECATED
RETIRED
```



Їхня семантика\:

- DRAFT — проєкт, який ще не є нормативно обов'язковим.
- EXPERIMENTAL — контракт, дозволений для контрольованого експериментального використання.
- STABLE — контракт із зафіксованою семантикою та визначеною політикою сумісності.
- DEPRECATED — контракт, який ще підтримується, але не повинен використовуватися в нових інтеграціях.
- RETIRED — контракт, який більше не допускається до нових операцій.

Перехід зі STABLE безпосередньо до RETIRED заборонений. Спочатку необхідний статус DEPRECATED, крім випадків критичної загрози безпеці або цілісності даних, коли окремо документується аварійне припинення підтримки.

# 4\. Канонічна модель даних SUBIT-CORE

Наступний крок — нормативно закріпити базові структури, від яких залежать усі модулі.

## 4.1. Entity

Entity представляє ідентифіковану сутність, стан якої можна описувати та відстежувати в часі.

Канонічна модель\:

`Entity = (id, type, state, context, provenance, revision)`

Нормалізоване представлення\:

```
Entity:
    id: EntityID
    type: EntityType

    state:
        schema_ref
        value

    context_ref: ContextID
    provenance_ref: ProvenanceID

    revision: UInt64
```



### Семантика

`id` — стабільний ідентифікатор сутності.

`type` — тип сутності, який визначає її семантичну область.

`state` — актуальна проєкція стану.

`context_ref` — контекст, у якому стан інтерпретується.

`provenance_ref` — походження інформації про сутність.

`revision` — номер ревізії проєкції.

Важливе розмежування\:

**Entity не є Event.**

Entity описує те, що існує в моделі на певному етапі. Event описує те, що відбулося.

Стан Entity є проєкцією прийнятих подій, а не заміною історії цих подій.

### Інваріанти Entity

`E-001`\: EntityID унікальний у межах визначеного простору ідентичності.

`E-002`\: Entity.type не може змінюватися без явної операції зміни типу.

`E-003`\: revision монотонно зростає після прийнятої зміни проєкції.

`E-004`\: кожна Entity має визначений контекст.

`E-005`\: кожна Entity має простежуване походження.

`E-006`\: зміна state не повинна знищувати попередню історію подій.

`E-007`\: однакова EntityID не означає однаковість стану в різних ревізіях.

## 4.2. Event

Event є незмінним записом про факт або прийняту зміну в системі.

Канонічна модель\:

`Event = (event_id, entity_ref, event_type, payload, context_ref, provenance_ref, time, causality)`

Структура\:

```
Event:
    event_id: EventID
    entity_ref: EntityID

    event_type: EventType
    payload:
        schema_ref
        value

    context_ref: ContextID
    provenance_ref: ProvenanceID

    time:
        occurred_at
        recorded_at

    causality:
        correlation_id
        causation_id
        parent_event_ids[]
        relation
```



### Важливе розмежування часу

`occurred_at` — час, коли подія відбулася відповідно до джерела.

`recorded_at` — час, коли подія була прийнята системою.

Ці значення можуть відрізнятися.

Не можна автоматично вважати час запису часом виникнення події.

### Інваріанти Event

`EV-001`\: event\_id унікальний.

`EV-002`\: прийнята подія незмінна.

`EV-003`\: event\_type має зареєстровану семантику.

`EV-004`\: payload відповідає схемі визначеного типу події.

`EV-005`\: контекст події повинен бути доступним або явно позначеним як зовнішнє посилання.

`EV-006`\: походження події повинно бути простежуваним.

`EV-007`\: причинні посилання не можуть посилатися на неіснуючі події без спеціального статусу unresolved.

`EV-008`\: глобальний порядок усіх подій не гарантується.

`EV-009`\: порядок змін однієї Entity має визначатися через ревізії та відповідний механізм упорядкування.

`EV-010`\: виправлення прийнятої події виконується новою подією, а не редагуванням старої.

## 4.3. Context

Контекст визначає умови, у яких значення або подія набувають конкретної інтерпретації.

Канонічна модель\:

`Context = (scope, environment, conditions, perspective)`

Структура\:

```
Context:
    context_id: ContextID

    scope:
        domain
        boundary
        granularity

    environment:
        system
        external_conditions

    conditions[]
    perspective:
        observer
        interpretation_mode
        assumptions[]

    parent_context_ref: Optional<ContextID>
    created_at
    schema_version
```



### Основні вимоги

1. Контекст не є довільним текстовим коментарем.
2. Контекст має типізовані поля.
3. Контекст може мати батьківський контекст.
4. Зміна умов інтерпретації створює новий контекст або нову контекстну ревізію.
5. Відсутність відомостей про контекст не можна трактувати як підтвердження універсальності значення.

Вводиться окремий статус контексту\:

```
CONTEXT_STATUS:
    COMPLETE
    PARTIAL
    UNKNOWN
    CONFLICTED
```



`UNKNOWN` не дорівнює `COMPLETE`\.

`CONFLICTED` не повинен автоматично перетворюватися на `UNKNOWN`\.

Це принципово важливо для майбутньої інтеграції з багатозначною логікою.

## 4.4. Provenance

Provenance описує походження даних, метод їх отримання та докази, на яких ґрунтується твердження.

Канонічна модель\:

`Provenance = (origin, author, source, method, timestamp, evidence)`

Структура\:

```
Provenance:
    provenance_id: ProvenanceID

    origin:
        origin_type
        origin_ref

    author:
        author_type
        author_ref

    source:
        source_type
        source_ref

    method:
        method_id
        method_version

    timestamp

    evidence[]:
        evidence_id
        evidence_type
        evidence_ref

    derivation[]:
        input_refs[]
        transformation_ref
```



### Види походження

Пропонується розрізняти\:

- DIRECT — безпосередньо отримані дані;
- DERIVED — результат обчислення;
- INFERRED — висновок на основі інших даних;
- IMPORTED — імпортовані дані;
- HUMAN\_ASSERTED — твердження, введене людиною;
- SYNTHETIC — внутрішньо згенеровані тестові або модельні дані.

Це розрізнення особливо важливе для SUBIT-AI та SUBIT-CHESS.

Внутрішньо згенерована позиція, людське твердження й результат зовнішнього імпорту не повинні зливатися в одну категорію походження.

# 5\. Event Envelope: контракт передавання подій

Канонічна подія та повідомлення, яким вона передається між модулями, не повинні ототожнюватися.

Тому вводиться Event Envelope.

`EventEnvelope = (Event, ContractMetadata, DeliveryMetadata)`

Структура\:

```
EventEnvelope:
    envelope_id
    event

    contract_metadata:
        contract_id
        contract_version
        schema_version

    producer:
        module_id
        module_version

    delivery:
        delivery_id
        idempotency_key
        attempt
        delivery_status
```



Цей рівень дозволяє змінювати механізм транспортування без зміни семантики самої події.

Наприклад, та сама Event може бути передана\:

- через локальну чергу;
- через внутрішній API;
- через файл;
- через мережевий транспорт.

Її семантика від цього не змінюється.

### Інваріанти Envelope

`EN-001`\: Event Envelope не змінює значення Event.

`EN-002`\: contract\_id повинен існувати в SCR.

`EN-003`\: producer.module\_id повинен бути зареєстрованим модулем.

`EN-004`\: schema\_version має бути сумісною з контрактом.

`EN-005`\: повторна доставка не повинна створювати дубльований логічний ефект.

`EN-006`\: доставка повідомлення не означає автоматичного прийняття події.

Останнє правило критично важливе: отримання повідомлення та його прийняття — різні операції.

# 6\. Версіонування

## 6.1. Розділення версій

Вводяться три незалежні поняття\:

`ModuleVersion`

`ContractVersion`

`SchemaVersion`

Вони не повинні автоматично збільшуватися синхронно.

Приклад\:

```
SUBIT-CPU:
    module_version: 0.4.2

    contracts:
        CPU.EXECUTE:
            contract_version: 1.1.0

        CPU.RESULT:
            contract_version: 1.0.0

    schemas:
        CPU.ExecutionResult:
            schema_version: 1.0.2
```



Модуль може змінити внутрішню реалізацію без зміни публічного контракту.

Водночас зміна семантики контракту може вимагати нової версії, навіть якщо версія модуля залишається незмінною на рівні його внутрішньої розробки.

## 6.2. Семантичне версіонування

Для контрактів застосовується формат\:

`MAJOR.MINOR.PATCH`

### MAJOR

Збільшується при несумісній зміні\:

- видалення обов'язкового поля;
- зміна типу поля;
- зміна семантики поля;
- зміна значення одиниці вимірювання;
- зміна правил інтерпретації;
- зміна обов'язкових передумов;
- зміна гарантій результату.

### MINOR

Збільшується при сумісному розширенні\:

- додавання необов'язкового поля;
- додавання нової необов'язкової можливості;
- розширення документації без зміни семантики;
- додавання нової операції, яка не порушує попередні контракти.

Розширення переліку значень enum не вважається автоматично сумісним. Воно потребує явного визначення політики відкритого або закритого переліку.

### PATCH

Збільшується при виправленні\:

- описок;
- уточнень документації;
- прикладів;
- помилок опису, які не змінюють нормативну поведінку.

PATCH не може приховувати семантичну зміну.

## 6.3. Правила сумісності схем

Для початкової версії встановлюються такі правила\:

1. Невідомі необов'язкові поля можуть ігноруватися, якщо це дозволено контрактом.
2. Невідомі обов'язкові поля роблять повідомлення несумісним.
3. Невідомі типи подій не можна мовчки відкидати.
4. Невідомі значення закритих enum вимагають карантину або відмови.
5. Невідомі значення відкритих enum зберігаються як непрозорі типізовані значення.
6. Значення поля не можна повторно використовувати з новою семантикою.
7. Перетворення між схемами має бути явним адаптером.

## 6.4. Депрекація

Пропонована політика\:

- контракт отримує статус DEPRECATED;
- визначається дата припинення підтримки;
- публікується рекомендований замінник;
- надається адаптер, якщо він технічно можливий;
- зберігається можливість читання історичних даних.

Для стабільних контрактів базова рекомендація — підтримувати стару версію протягом щонайменше двох наступних minor-релізів або 90 днів, залежно від того, який період довший.

Це початкове нормативне припущення, яке потребує остаточного затвердження.

# 7\. Алгоритм перевірки сумісності

Вводиться функція\:

`CanConnect(Producer, Consumer, Contract)`

Її завдання — визначити, чи може один модуль передавати дані іншому без порушення контракту.

## 7.1. Умови сумісності

З'єднання допустиме, якщо\:

1. Contract існує.
2. Статус Contract допускає використання.
3. Producer реалізує необхідну версію контракту.
4. Consumer підтримує версію, яку надає Producer.
5. Схема сумісна.
6. Типи даних збігаються.
7. Семантичний домен сумісний.
8. Обов'язкові залежності задоволені.
9. Не порушено інваріанти.
10. Необхідні можливості та дозволи наявні.

## 7.2. Псевдокод

```
function CanConnect(producer, consumer, contract):

    if contract == null:
        return REJECT("CONTRACT_NOT_FOUND")

    if contract.status == RETIRED:
        return REJECT("CONTRACT_RETIRED")

    if contract.status == DRAFT:
        return REJECT("CONTRACT_NOT_RELEASED")

    if not producer.provides(contract.contract_id):
        return REJECT("PRODUCER_MISSING_CONTRACT")

    if not consumer.requires_or_accepts(contract.contract_id):
        return REJECT("CONSUMER_CONTRACT_MISMATCH")

    if not version_range_accepts(
        consumer.accepted_versions,
        producer.contract_version
    ):
        return REJECT("VERSION_INCOMPATIBLE")

    if not schema_compatible(
        producer.schema,
        consumer.schema_profile
    ):
        return REJECT("SCHEMA_INCOMPATIBLE")

    if not semantic_domain_compatible(
        producer.semantic_domain,
        consumer.semantic_domain
    ):
        return REJECT("SEMANTIC_DOMAIN_MISMATCH")

    if not dependencies_satisfied(contract):
        return REJECT("DEPENDENCY_UNSATISFIED")

    if not invariants_declared(contract):
        return REJECT("INVARIANTS_MISSING")

    return ACCEPT
```



Функція не повинна обмежуватися перевіркою номерів версій.

Два контракти з однаковою версією можуть бути семантично несумісними, якщо їхні домени або інтерпретації різні.

# 8\. Міжмодульна інтеграція

Тепер визначимо базову інтеграційну топологію.

## 8.1. SUBIT-CORE

**Відповідальність\:**

- базові типи;
- ідентичність сутностей;
- канонічні структури;
- контекст;
- provenance;
- причинність;
- контрактні інваріанти.

CORE не повинен залежати від AI, CHESS або інших прикладних модулів.

Його роль — надавати фундамент, а не реалізовувати прикладну поведінку.

## 8.2. SUBIT-LANG

Потік\:

`Input → Parse → Typed Command → CommandEnvelope`

LANG повинен відокремлювати\:

- синтаксичну структуру;
- семантичну інтерпретацію;
- контекст;
- невизначеність;
- походження команди.

LANG не має права самостійно створювати підтверджені факти про виконання операцій.

Результат аналізу природної мови — це команда або пропозиція, а не вже здійснена подія.

## 8.3. SUBIT-DATA

Відповідальність\:

- незмінне збереження прийнятих подій;
- дедуплікація;
- індексація;
- відтворення історії;
- побудова проєкцій;
- контроль цілісності.

DATA не повинна самостійно переосмислювати семантику подій.

Вона зберігає дані відповідно до зареєстрованих контрактів.

## 8.4. SUBIT-RUNTIME

RUNTIME є координатором виконання.

Його функції\:

- приймання команд;
- перевірка контрактів;
- маршрутизація;
- контроль дозволів;
- координація CPU, AI та TOOLS;
- перевірка результатів;
- передавання прийнятих подій до DATA.

RUNTIME не повинен самовільно змінювати семантику CORE.

## 8.5. SUBIT-CPU

CPU отримує формалізовані операції та повертає результат виконання.

Важливе правило\:

**SUBIT-CPU не записує події безпосередньо до Event Store.**

CPU повертає результат або пропозицію переходу стану. RUNTIME перевіряє результат і передає його до DATA через визначений механізм фіксації.

Це відокремлює обчислення від прийняття та збереження факту.

## 8.6. SUBIT-AI

AI може\:

- аналізувати події;
- оцінювати контексти;
- будувати гіпотези;
- формувати рекомендації;
- генерувати пропозиції переходів;
- оцінювати невизначеність.

Але\:

`AI inference ≠ Accepted Event`

Висновок AI не стає фактом лише через те, що його сформував інтелектуальний модуль.

Для прийняття результату необхідні відповідні перевірки, політика та реєстрація походження.

## 8.7. SUBIT-TOOLS

TOOLS виконує зовнішні дії тільки через авторизовані контракти.

Типовий цикл\:

`ToolIntent → Authorization → Execution → ToolResult`

Кожна зовнішня дія повинна мати\:

- ідентифікатор наміру;
- контекст;
- походження;
- дозвіл;
- результат;
- статус виконання.

Повторна доставка ToolIntent не повинна автоматично створювати повторну зовнішню дію.

Для цього використовується idempotency key.

## 8.8. SUBIT-VERIFICATION

VERIFICATION перевіряє\:

- структуру даних;
- відповідність схемам;
- семантичні інваріанти;
- сумісність версій;
- причинні посилання;
- коректність переходів станів;
- дотримання політик виконання.

VERIFICATION не повинен підміняти собою джерело даних.

Його результат — це висновок перевірки з власним provenance.

# 9\. Канонічний потік виконання

Узагальнена схема\:

**SUBIT-LANG**

Інтерпретація та типізована команда

**SUBIT-RUNTIME**

Контракти, контекст, дозволи та маршрутизація

**SUBIT-CPU**

Формальне виконання

**SUBIT-AI**

Аналіз і пропозиції

**SUBIT-TOOLS**

Зовнішні дії

**SUBIT-VERIFICATION**

Перевірка результатів

**SUBIT-DATA**

Фіксація прийнятих подій і відтворення стану

SUBIT-CORE надає канонічні типи та інваріанти всім модулям; SUBIT Contract Registry визначає допустимі взаємодії.

Це логічна схема, а не твердження про вже реалізовану систему.

## 9.1. Послідовність

```
1. LANG створює CommandEnvelope.

2. RUNTIME перевіряє:
       contract
       schema
       context
       provenance
       permissions

3. RUNTIME визначає виконавця:
       CPU
       AI
       TOOLS
       або комбінацію модулів

4. Виконавець повертає результат.

5. VERIFICATION перевіряє результат.

6. RUNTIME формує Event.

7. DATA атомарно приймає Event
   та забезпечує її збереження.

8. Reducer оновлює Entity projection.

9. Результат стає доступним
   для наступних операцій.
```

# 10\. Атомарність, повторна доставка та відтворення

Цей розділ визначає важливі гарантії інтеграції.

## 10.1. Відокремлення обчислення від фіксації

Результат обчислення не повинен автоматично змінювати стан системи.

Вводиться послідовність\:

`Compute → Validate → Commit → Project`

Кожен етап має окремий статус.

## 10.2. Ідемпотентність

Для кожної події використовується стабільний event\_id.

Для кожного запиту зовнішньої дії — idempotency\_key.

Умовна функція прийняття\:

```
function AppendEvent(event):

    if EventStore.contains(event.event_id):
        return DUPLICATE(event.event_id)

    if not validate_event(event):
        return REJECTED

    persist_atomically(event)

    return ACCEPTED(event.event_id)
```



Повторне надсилання вже прийнятої події не створює нову логічну подію.

Водночас різні події з однаковим payload можуть бути законними, якщо вони описують різні факти або відбулися в різних контекстах.

## 10.3. Гарантії доставки

Для початкової архітектури пропонується\:

- доставка повідомлень — at-least-once;
- логічна дедуплікація — через event\_id;
- порядок подій — на рівні Entity або іншого явно визначеного потоку;
- глобальний порядок — не гарантується;
- exactly-once delivery — не заявляється.

Це важливе обмеження: exactly-once не можна проголошувати лише на підставі наявності унікального ідентифікатора.

## 10.4. Outbox

Для узгодження фіксації події та її передавання іншим компонентам пропонується transactional outbox.

```
CommitTransaction:
    validate(event)

    begin transaction

        append EventStore(event)

        append Outbox(
            event_id = event.event_id,
            delivery_status = PENDING
        )

    commit transaction
```



Після фіксації окремий механізм доставки передає повідомлення адресатам.

Якщо доставка переривається, outbox дозволяє повторити її без повторного створення самої події.

Це запропонований архітектурний механізм. Його конкретна реалізація залежить від обраного сховища та транзакційної моделі.

# 13\. Перевірки та критерії прийняття

На цьому етапі визначаються критерії, але не заявляється, що вони вже виконані.

## 13.1. Структурні перевірки

- [ ] Усі типи CORE мають унікальні ідентифікатори.
- [ ] Усі контракти мають власника.
- [ ] Усі контракти мають версію.
- [ ] Усі контракти мають семантичний домен.
- [ ] Усі залежності існують у SCR.
- [ ] Циклічні фундаментальні залежності відсутні.

## 13.2. Перевірки Entity/Event

- [ ] EntityID не конфліктують.
- [ ] EventID не конфліктують.
- [ ] Event не змінюється після прийняття.
- [ ] Revision зростає монотонно.
- [ ] Події можна відтворити в межах визначеної моделі.
- [ ] Контекст і provenance зберігаються при передаванні.

## 13.3. Перевірки сумісності

Необхідно створити контрольні сценарії\:

1. Producer 1.0.0 → Consumer 1.0.0: сумісний випадок.
2. Producer 1.1.0 → Consumer 1.0.0: сумісність лише за явної підтримки додаткових полів.
3. Producer 2.0.0 → Consumer 1.0.0: відмова без адаптера.
4. Невідоме необов'язкове поле: контрольоване ігнорування.
5. Невідоме обов'язкове поле: відмова.
6. Невідомий тип події: карантин.
7. Невідоме значення закритого enum: відмова.
8. Повторна доставка одного event\_id: дедуплікація.
9. Два різні event\_id з однаковим payload: не вважати автоматично дублями.
10. Несумісні семантичні домени: відмова незалежно від однакової версії.

## 13.4. Перевірки типового розділення

Особливо важливий набір\:

```
WHO.ME = 10
WHERE.EAST = 10
WHEN.SPRING = 10
FOUR.T = 10
```



Очікуваний результат\:

- усі чотири значення мають різні типи;
- пряме присвоєння між типами заборонене;
- рівність бітового представлення не створює семантичної тотожності;
- перетворення можливе лише через окремий контракт.

# 14\. Ризики та способи їх обмеження

**Ризик 1. Надмірна централізація SCR.**

Якщо кожна зміна потребуватиме ручного узгодження всього екосистемного реєстру, розвиток сповільниться.

Рішення: централізована нормативна модель, але локальні маніфести й незалежна валідація модулів.

**Ризик 2. Надмірне ускладнення Entity/Event.**

Занадто велика кількість обов'язкових полів ускладнить прості модулі.

Рішення: мінімальне обов'язкове ядро плюс типізовані розширення.

**Ризик 3. Хибна сумісність за SemVer.**

Однакові номери версій не гарантують однакової семантики.

Рішення: перевірка схем, інваріантів і семантичного домену, а не лише версій.

**Ризик 4. Втрата provenance у похідних даних.**

Це зробить неможливим надійний аудит результатів AI або CPU.

Рішення: обов'язкові посилання на джерела й методи трансформації.

**Ризик 5. Помилкове трактування AI-висновків як фактів.**

Рішення: відокремити Proposal, Decision і Accepted Event.

**Ризик 6. Дублювання зовнішніх дій.**

Рішення: idempotency key, журнал намірів і результатів, явні стани виконання.

**Ризик 7. Змішування FOUR і SUBIT-64.**

Рішення: незалежні типи, простори ідентичності, контракти перетворення та окремі перевірки.

# 15\. Відкриті питання

Для завершення v0.1.0 залишаються питання, які не слід вирішувати прихованими припущеннями.

1. **Формат контрактів\:** JSON Schema, власна типізована мова SUBIT-LANG чи проміжне канонічне представлення з можливістю генерації JSON Schema?
2. **Ідентифікатори\:** UUID, ULID чи типізовані SUBIT-ID? Потрібно оцінити вимоги до глобальної унікальності, порядку та відтворюваності.
3. **Контекст\:** чи повинен кожний Context бути незмінним об'єктом, чи допускається версіонована контекстна проєкція?
4. **Provenance\:** який мінімальний набір доказів обов'язковий для різних класів тверджень?
5. **Event ordering\:** чи достатньо ревізій Entity, чи потрібен окремий механізм послідовності для кожного агрегату?
6. **Reducer\:** чи повинен кожен модуль мати власний набір reducer-функцій, чи частина редукторів має бути стандартизована CORE?
7. **SCR governance\:** хто має право переводити контракт зі статусу DRAFT до STABLE і які докази для цього потрібні?
8. **Адаптери\:** чи повинні адаптери бути окремими зареєстрованими модулями, чи можуть вони бути частиною RUNTIME?
9. **Безпека\:** чи вводити окрему модель підписів, прав доступу та криптографічної перевірки provenance вже у v0.1.0, чи залишити її наступним інкрементом?

Моя архітектурна рекомендація: не відкладати типізацію, provenance та версіонування, але не прив'язувати першу версію CORE до конкретного транспортного протоколу, бази даних або криптографічного алгоритму.

## Підсумок інкременту

У межах цього проєкту специфікації зроблено наступний архітектурний крок: від матриці залежностей між модулями — до формалізованої системи контрактів, версій і сумісності.

Найважливіше рішення полягає в розмежуванні чотирьох рівнів\:

- **Entity** — що описується системою;
- **Event** — що відбулося;
- **Context** — за яких умов це має значення;
- **Provenance** — звідки походить інформація.

Contract Registry визначає, як ці структури можуть передаватися та інтерпретуватися різними модулями.

Це створює основу для незалежного розвитку LANG, DATA, RUNTIME, CPU, AI, TOOLS і VERIFICATION без втрати цілісності екосистеми.
