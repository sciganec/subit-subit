# SUBIT-CPU v0.1
## Universal Adaptive Computational Engine

**Версія:** 0.1  
**Статус:** Архітектурна специфікація / базовий проєкт реалізації  
**Тип:** Універсальне адаптивне обчислювальне ядро  
**Модель:** Computational Graph + Intermediate Representation + Adaptive Optimizer + Execution Runtime  
**Основна мета:** Оптимізація виконання алгоритмів і складних обчислювальних задач на основі структурного аналізу, контексту, залежностей та доступних обчислювальних ресурсів.

---

# 1. Загальна концепція

SUBIT-CPU — це універсальне програмне обчислювальне ядро, призначене для аналізу, трансформації, оптимізації та виконання обчислювальних задач різних типів.

На відміну від традиційної моделі процесора, яка передусім виконує задану послідовність інструкцій, SUBIT-CPU має працювати з обчислювальною задачею на декількох рівнях:

1. Рівень окремих операцій.
2. Рівень структур і залежностей між операціями.
3. Рівень алгоритмів.
4. Рівень обчислювальних стратегій.
5. Рівень адаптивного вибору способу виконання.

Ключова гіпотеза проєкту:

**Якщо обчислювальне ядро здатне аналізувати не лише окремі операції, а й структуру всієї задачі, її залежності, контекст і доступні ресурси, воно може знаходити ефективніші способи виконання складних алгоритмів.**

SUBIT-CPU не повинен обмежуватися одним типом обчислень. Він має підтримувати взаємодію декількох обчислювальних доменів:

- числового;
- логічного;
- матричного;
- векторного;
- структурного;
- графового;
- комбінаторного;
- символьного;
- адаптивного.

Belnap–Dunn FOUR є одним із логічних доменів SUBIT-CPU, але не визначає всю архітектуру ядра.

## 1.1. Основне архітектурне визначення

SUBIT-CPU складається з таких компонентів:

SUBIT-CPU = COMPUTATIONAL CORE + IR + GRAPH ENGINE + OPTIMIZER + EXECUTION ENGINE + CONTEXT + PROVENANCE + VALIDATION

Де:

- COMPUTATIONAL CORE — базові обчислювальні примітиви.
- IR — проміжне представлення обчислень.
- GRAPH ENGINE — побудова та аналіз графів обчислювальних залежностей.
- OPTIMIZER — пошук ефективніших способів виконання.
- EXECUTION ENGINE — виконання оптимізованих обчислювальних планів.
- CONTEXT — контекст виконання.
- PROVENANCE — походження даних і результати їхніх трансформацій.
- VALIDATION — перевірка коректності трансформацій і результатів.

# 2. Архітектурні принципи

## 2.1. Computational Plurality

SUBIT-CPU не повинен припускати, що всі обчислення належать до одного математичного або логічного домену.

Числові операції, логічні операції, матричні перетворення, графові алгоритми та комбінаторний пошук мають різну внутрішню структуру.

Ядро повинно зберігати цю відмінність, але забезпечувати можливість взаємодії між доменами.

## 2.2. Contextual Execution

Результат операції не завжди можна оцінити незалежно від контексту її виконання.

Контекст може включати:

- тип задачі;
- вимоги до точності;
- обмеження пам'яті;
- доступні процесорні ресурси;
- допустимий рівень паралелізму;
- обмеження часу;
- вимоги до відтворюваності;
- походження вхідних даних;
- вимоги до перевірки результату.

Одна й та сама операція за різних умов може потребувати різних стратегій виконання.

## 2.3. Adaptive Optimization

Оптимізатор повинен не просто застосовувати набір наперед визначених правил, а оцінювати доступні варіанти виконання.

Наприклад:

- послідовне виконання;
- пакетне виконання;
- векторизація;
- паралельне виконання;
- кешування проміжних результатів;
- усунення повторних обчислень;
- зміна порядку незалежних операцій;
- використання спеціалізованого обчислювального примітива.

Адаптивність означає вибір стратегії відповідно до структури задачі та умов виконання.

## 2.4. Structural Preservation

Оптимізація не повинна знищувати інформацію про структуру задачі.

Зокрема, ядро повинно зберігати:

- залежності між операціями;
- порядок, якщо він семантично важливий;
- типи даних;
- контекст;
- походження результатів;
- умови коректності;
- обмеження допустимих трансформацій.

## 2.5. Verified Transformation

Кожна оптимізаційна трансформація повинна мати формально або емпірично визначені умови застосування.

Оптимізатор не повинен змінювати поведінку алгоритму лише тому, що альтернативний варіант здається швидшим.

Для кожного правила трансформації необхідно визначити:

- передумови;
- допустимий діапазон застосування;
- очікуваний ефект;
- можливі побічні наслідки;
- спосіб перевірки еквівалентності;
- критерії відмови від трансформації.

# 3. Загальна архітектура

Архітектура SUBIT-CPU v0.1 передбачає дев'ять основних підсистем.

## 3.1. Computational Core

Базове обчислювальне ядро.

Відповідає за:

- арифметичні операції;
- логічні операції;
- порівняння;
- перетворення типів;
- базові операції над структурами даних;
- контроль помилок;
- узгодження типів.

Важливо: SUBIT-CPU не повинен самостійно реалізовувати всі можливі математичні алгоритми. Він має використовувати ефективні системні та спеціалізовані примітиви там, де це доцільно.

Власна цінність ядра полягає передусім у тому, як воно організовує, трансформує та виконує обчислення.

## 3.2. Intermediate Representation (IR)

Проміжне представлення — центральний архітектурний компонент.

Воно дозволяє описати обчислювальну задачу незалежно від конкретного способу її виконання.

IR повинно містити:

- операції;
- операнди;
- типи даних;
- залежності;
- константи;
- умови;
- метадані;
- обмеження;
- інформацію про контекст;
- інформацію про походження даних.

IR є спільною мовою між програмою, оптимізатором і механізмом виконання.

## 3.3. Computational Graph Engine

Механізм побудови обчислювального графа.

Граф представляє задачу як множину операцій та залежностей між ними.

G = (V, E)

Де:

- V — множина обчислювальних вузлів;
- E — множина залежностей між вузлами.

Вузол графа представляє операцію або обчислювальний етап.

Ребро представляє залежність, передачу даних або інше обмеження порядку виконання.

Граф дозволяє визначити:

- які операції незалежні;
- які операції можуть виконуватися паралельно;
- які операції можна об'єднати;
- які результати можна повторно використати;
- які обчислення є надлишковими;
- де виникають вузькі місця;
- які трансформації є допустимими.

## 3.4. Adaptive Optimizer

Оптимізатор аналізує IR та обчислювальний граф, після чого формує альтернативні плани виконання.

Він повинен працювати на п'яти рівнях.

**Рівень 1. Instruction Optimization**

Оптимізація окремих операцій:

- constant folding;
- constant propagation;
- усунення зайвих перетворень;
- спрощення виразів;
- усунення тотожних операцій.

**Рівень 2. Data Optimization**

Оптимізація роботи з даними:

- повторне використання результатів;
- кешування;
- зменшення копіювання;
- пакетна обробка;
- оптимізація доступу до пам'яті.

**Рівень 3. Execution Optimization**

Оптимізація способу виконання:

- зміна порядку незалежних операцій;
- векторизація;
- паралелізація;
- групування операцій;
- вибір відповідного виконавчого механізму.

**Рівень 4. Algorithm Optimization**

Оптимізація структури алгоритму:

- усунення повторних проходів;
- використання проміжних індексів;
- зміна представлення даних;
- вибір альтернативного алгоритму;
- скорочення обсягу проміжних обчислень.

**Рівень 5. Strategy Optimization**

Оптимізація загальної стратегії:

- вибір між точним і наближеним методом, якщо обидва дозволені;
- вибір між послідовним і паралельним виконанням;
- вибір між попереднім обчисленням і обчисленням на вимогу;
- адаптація до обмежень часу та пам'яті;
- вибір оптимального способу розбиття задачі.

Оптимізатор повинен мати право не застосовувати трансформацію, якщо її користь не підтверджена або якщо вона порушує семантику задачі.

## 3.5. Execution Engine

Механізм фактичного виконання.

Передбачаються такі режими:

- INTERPRETED — інтерпретоване виконання;
- SEQUENTIAL — послідовне виконання;
- VECTORIZED — векторизоване виконання;
- PARALLEL — паралельне виконання;
- BATCHED — пакетне виконання;
- ADAPTIVE — адаптивний вибір режиму.

У v0.1 обов'язковими є інтерпретований і послідовний режими.

Решта режимів є архітектурними розширеннями, які вводяться після перевірки базового механізму.

## 3.6. Context Engine

Підсистема контексту.

Вона описує умови, в яких виконується задача.

Приклад:

```javascript
const context = {
  objective: "minimize_runtime",

  constraints: {
    maxMemoryBytes: 256 * 1024 * 1024,
    maxExecutionTimeMs: 5000,
    deterministic: true,
    exactResultRequired: true
  },

  resources: {
    cpuCores: 4,
    simdAvailable: false,
    parallelExecution: false
  },

  optimization: {
    level: 2,
    allowApproximation: false,
    allowReordering: true,
    allowCaching: true
  }
};
```

Цей об'єкт є прикладом API, а не гарантією автоматичного виявлення всіх ресурсів.

## 3.7. Provenance Engine

Підсистема походження даних.

Вона повинна забезпечувати можливість відповісти на питання:

- Звідки походить значення?
- Які операції його сформували?
- Які дані були використані?
- Які трансформації застосовувалися?
- Який оптимізаційний план виконав задачу?
- Чи було значення отримане прямим обчисленням або кешуванням?

Provenance не повинен примусово створювати повний журнал кожної низькорівневої операції.

Передбачаються режими:

- NONE;
- BASIC;
- DETAILED;
- FULL.

Режим FULL може мати значний вплив на продуктивність і тому не повинен бути стандартним для звичайного виконання.

## 3.8. Validation Engine

Підсистема перевірки.

Відповідає за:

- перевірку типів;
- перевірку коректності IR;
- перевірку залежностей;
- перевірку допустимості трансформацій;
- перевірку результатів;
- виявлення помилок виконання;
- порівняння контрольних результатів.

Вона повинна підтримувати декілька рівнів перевірки:

1. Structural validation.
2. Type validation.
3. Semantic validation.
4. Runtime validation.
5. Differential validation.

## 3.9. Memory Manager

Керує пам'яттю, проміжними результатами та їхнім життєвим циклом.

Основні функції:

- allocation;
- deallocation;
- memory reuse;
- buffer management;
- temporary storage;
- cache management;
- memory profiling.

У v0.1 допускається використання стандартного менеджера пам'яті мови реалізації.

Власний менеджер пам'яті має вводитися лише після отримання результатів профілювання.

# 4. Intermediate Representation — SUBIT-IR

## 4.1. Призначення

SUBIT-IR — універсальне проміжне представлення обчислювальних задач.

Його головне призначення — відокремити опис обчислення від способу виконання.

Наприклад, користувач може визначити:

```text
A = X + Y
B = A * Z
C = B + W
```

SUBIT-CPU повинен представити цю задачу як граф:

```text
X ─┐
   ├─ ADD ─ A ─┐
Y ─┘           │
               ├─ MUL ─ B ─┐
Z ─────────────┘           │
                           ├─ ADD ─ C
W ─────────────────────────┘
```

Оптимізатор аналізує структуру, а не лише послідовність текстових виразів.

## 4.2. Структура вузла

Базовий вузол SUBIT-IR:

```javascript
{
  id: "node_001",

  op: "ADD",

  domain: "NUMERIC",

  inputs: [
    "value_x",
    "value_y"
  ],

  output: {
    id: "value_a",
    type: "F64"
  },

  attributes: {},

  metadata: {
    pure: true,
    deterministic: true,
    estimatedCost: null
  }
}
```

Поля:

- id — унікальний ідентифікатор вузла;
- op — операція;
- domain — обчислювальний домен;
- inputs — вхідні значення;
- output — вихідне значення;
- attributes — параметри операції;
- metadata — додаткова інформація.

`estimatedCost: null` означає, що оцінка вартості ще не отримана.

Оцінки вартості не можна вважати фактичними вимірюваннями.

## 4.3. Типи даних

Базова система типів:

### Числові

- I8;
- I16;
- I32;
- I64;
- U8;
- U16;
- U32;
- U64;
- F32;
- F64.

### Логічні

- BOOL;
- FOUR.

### Структурні

- ARRAY;
- VECTOR;
- MATRIX;
- TENSOR;
- GRAPH;
- SET;
- MAP;
- TREE.

### Службові

- STRING;
- BYTES;
- NULL;
- ANY;
- RESULT;
- ERROR.

Це початковий перелік. Типова система має бути розширюваною.

## 4.4. Типізація операцій

Кожна операція повинна мати контракт:

- допустимі типи входів;
- тип виходу;
- семантику;
- умови виконання;
- правила помилок;
- властивості детермінованості;
- властивості чистоти.

Наприклад, операція ADD для F64 і ADD для FOUR — це різні операції з різними семантичними контрактами.

Однакова назва не означає однакову математичну поведінку.

# 5. Computational Domains

SUBIT-CPU має підтримувати окремі обчислювальні домени.

## 5.1. Numeric Domain

Числовий домен.

Операції:

- ADD;
- SUB;
- MUL;
- DIV;
- MOD;
- ABS;
- MIN;
- MAX;
- POW;
- SQRT;
- COMPARE;
- CONVERT.

Умови:

- контроль переповнення;
- контроль ділення на нуль;
- визначення правил округлення;
- контроль точності;
- явна політика роботи з NaN та нескінченностями.

Оптимізатор не має права змінювати порядок операцій з плаваючою комою без відповідного дозволу.

Наприклад:

```text
(A + B) + C
```

не завжди семантично еквівалентне:

```text
A + (B + C)
```

через обмежену точність представлення чисел.

## 5.2. Logic Domain

Логічний домен.

Підтримує:

- BOOL;
- FOUR;
- AND;
- OR;
- NOT;
- XOR;
- SJOIN;
- SMEET;
- BXOR.

Для FOUR використовується чотиризначна логіка Белнапа–Данна.

Значення:

- N = 00 — NEITHER;
- F = 01 — FALSE;
- T = 10 — TRUE;
- B = 11 — BOTH.

Кожне значення представляється парою:

```text
(t, f)
```

де:

- t — наявність позитивного свідчення;
- f — наявність негативного свідчення.

Операції:

```text
NOT(a) = (a.f, a.t)

AND(a,b) = (
  a.t AND b.t,
  a.f OR b.f
)

OR(a,b) = (
  a.t OR b.t,
  a.f AND b.f
)

SJOIN(a,b) = (
  a.t OR b.t,
  a.f OR b.f
)

SMEET(a,b) = (
  a.t AND b.t,
  a.f AND b.f
)

BXOR(a,b) = (
  a.t XOR b.t,
  a.f XOR b.f
)
```

SUBIT-CPU повинен розрізняти:

- truth ordering;
- knowledge ordering.

FOUR не можна ототожнювати з BOOL або з шестибітною системою SUBIT-64.

### FOUR_WORD

Для компактного представлення восьми FOUR-значень передбачається 16-бітне слово:

```text
FOUR_WORD = 16 bits = 8 FOUR cells
```

Це створює можливість пакетної обробки восьми FOUR-значень.

Однак фактичне прискорення має бути виміряне, а не припущене.

## 5.3. Matrix Domain

Матричний домен.

Операції:

- MATRIX_CREATE;
- MATRIX_ADD;
- MATRIX_SUB;
- MATRIX_MUL;
- MATRIX_TRANSPOSE;
- MATRIX_SCALE;
- MATRIX_REDUCE;
- MATRIX_DECOMPOSE.

Підтримка:

- розмірностей;
- сумісності форм;

# 6. Adaptive Optimizer

## 6.1. Загальна модель

Оптимізатор отримує:

```text
INPUT:
  IR
  COMPUTATIONAL GRAPH
  CONTEXT
  RESOURCE PROFILE
  OPTIMIZATION POLICY

OUTPUT:
  OPTIMIZED IR
  EXECUTION PLAN
  OPTIMIZATION REPORT
```

## 6.2. Оптимізаційні правила

Кожне правило має описуватися окремим об'єктом.

Приклад:

```javascript
{
  id: "OPT_CONSTANT_FOLDING",

  level: "INSTRUCTION",

  domain: ["NUMERIC"],

  preconditions: [
    "ALL_INPUTS_CONSTANT",
    "PURE_OPERATION"
  ],

  transformation: "EVALUATE_AT_COMPILE_TIME",

  correctness: {
    semanticEquivalenceRequired: true
  },

  costModel: {
    expectedBenefit: "REDUCE_RUNTIME_OPERATIONS"
  }
}
```

Це декларація правила, а не готовий механізм його виконання.

## 6.3. Початковий набір оптимізацій

У v0.1 необхідно реалізувати:

1. Constant Folding.
2. Constant Propagation.
3. Dead Code Elimination.
4. Common Subexpression Elimination.
5. Identity Elimination.
6. Dependency Analysis.
7. Topological Scheduling.
8. Operation Fusion — лише для операцій з доведеною сумісністю семантики.
9. Reuse of Intermediate Results.

Кожна оптимізація повинна мати окремі тести.

## 6.4. Cost Model

Оптимізатор повинен оцінювати вартість альтернативних планів.

Початкова модель:

```text
TOTAL_COST =
  COMPUTATION_COST
  + MEMORY_COST
  + DATA_TRANSFER_COST
  + SCHEDULING_COST
  + VALIDATION_COST
  + SYNCHRONIZATION_COST
```

Це концептуальна модель. У реальній реалізації кожен компонент повинен бути визначений вимірюваними величинами або чітко позначеними евристичними оцінками.

Наприклад:

- кількість операцій;
- обсяг пам'яті;
- кількість копіювань;
- кількість проміжних виділень;
- кількість переходів між виконавчими механізмами;
- накладні витрати паралелізації.

## 6.5. Adaptive Decision

Оптимізатор повинен порівнювати доступні плани:

```text
PLAN A: SEQUENTIAL
PLAN B: VECTORIZED
PLAN C: PARALLEL
PLAN D: BATCHED
```

Для кожного плану визначаються:

- допустимість;
- очікувана вартість;
- ресурсні вимоги;
- ризики;
- умови перевірки.

Вибирається план з найкращим очікуваним результатом, який задовольняє обмеження задачі.

Якщо оцінки недостатньо надійні, оптимізатор повинен вибирати консервативний варіант.

# 8. Context, Provenance та Knowledge Structure

SUBIT-CPU повинен розрізняти обчислювальне значення та інформацію про нього.

Це принципово важливо.

Значення саме по собі не містить усієї інформації про:

- використані правила;
- трансформації;
- рівень перевірки;
- контекст застосування.

Для цього передбачається модель:

```text
KNOWLEDGE =
  STATE
  + CONTEXT
  + PROVENANCE
  + DYNAMICS
  + RULE
  + META-RULE
```

Ця модель є концептуальною основою інформаційної архітектури SUBIT-CPU.

У практичній реалізації компоненти можуть зберігатися окремо.

## 8.1. State

Фактичне обчислювальне значення.

## 8.2. Context

Умови, в яких значення було отримане або використовується.

## 8.3. Provenance

Історія походження значення.

## 8.4. Dynamics

Зміни значення або структури в часі.

## 8.5. Rule

Правило, за яким було отримано результат.

## 8.6. Meta-rule

Правило вибору, зміни або перевірки інших правил.

SUBIT-CPU не повинен примусово включати всі ці компоненти в кожне числове значення.

Вони мають бути доступні як окремий шар метаданих.

# 9. Transactional Integrity

SUBIT-CPU повинен підтримувати контрольовані транзакційні операції.

Базова модель:

```text
PREPARE
  ↓
EXECUTE
  ↓
VALIDATE
  ↓
COMMIT
```

У разі помилки:

```text
ABORT
  ↓
ROLLBACK
```

Однак транзакційність не повинна автоматично застосовуватися до кожної арифметичної операції.

Це створило б надмірні накладні витрати.

Тому передбачаються три режими:

### NONE

Звичайне виконання без транзакційного журналу.

### SELECTIVE

Транзакційний контроль для вибраних вузлів, операцій або груп операцій.

### FULL

Повний контроль транзакційних меж.

У v0.1 обов'язковим є SELECTIVE як архітектурна можливість, навіть якщо початкова реалізація буде обмеженою.

# 10. API

```javascript

const cpu = createSubitCPU({
  optimizationLevel: 2,
  executionMode: "AUTO",

const result = await cpu.run({
  input: {
    x: 10,
    y: 20,
    z: 3

    return (x + y) * z;
  }

console.log(result.value);
```

Це цільовий приклад API. Він не означає, що відповідна реалізація вже існує.

```javascript
cpu.run(task, options);

cpu.profile(task, options);

cpu.validate(result);

cpu.benchmark(task, options);

cpu.getCapabilities();
```

# 12. Benchmark Engine

SUBIT-CPU не можна оцінювати лише за фактом успішного виконання задач.

Основна мета — встановити, чи забезпечує ядро реальну перевагу порівняно з базовим виконанням.

Тому benchmark-система є обов'язковою частиною проєкту.

## 12.1. Базові категорії тестів

### Numeric Benchmarks

- арифметичні цикли;
- масиви чисел;
- редукції;
- сортування;
- повторні обчислення;
- числові перетворення.

### Matrix Benchmarks

- додавання матриць;
- множення матриць;
- транспонування;
- редукції;
- операції над великими масивами.

### Graph Benchmarks

- обхід графа;
- пошук шляхів;
- аналіз компонентів;
- виявлення залежностей;
- топологічне сортування.

### Combinatorial Benchmarks

- перебір;
- пошук;
- обмежений пошук;
- аналіз дерев станів;
- задачі з повторюваними підобчисленнями.

### Logic Benchmarks

- BOOL;
- FOUR;
- пакетні FOUR-операції;
- логічні перетворення;
- аналіз суперечливих і неповних даних.

### Structural Benchmarks

- порівняння структур;
- трансформація дерев;
- фільтрація;
- пошук повторюваних підструктур;
- аналіз залежностей.

## 12.2. Режими порівняння

Кожна задача має виконуватися щонайменше у трьох режимах:

1. BASELINE — базова реалізація без SUBIT-CPU.
2. SUBIT-CPU RAW — виконання через ядро без оптимізатора.
3. SUBIT-CPU OPTIMIZED — виконання через ядро з оптимізатором.

За потреби додається четвертий режим:

4. SPECIALIZED — реалізація із застосуванням спеціалізованого алгоритму або бібліотеки.

Це допоможе визначити, чи оптимізатор справді покращує виконання, чи лише додає накладні витрати.

## 12.3. Метрики

Обов'язкові метрики:

- execution time;
- memory usage;
- operation count;
- intermediate allocations;
- data transfer;
- scheduling overhead;
- optimization overhead;
- validation overhead;
- correctness.

## 12.4. Основна метрика

```text
SPEEDUP = BASELINE_TIME / SUBIT_CPU_TIME
```

Інтерпретація:

- SPEEDUP > 1 — SUBIT-CPU швидший;
- SPEEDUP = 1 — однакова швидкість;
- SPEEDUP < 1 — SUBIT-CPU повільніший.

Для оцінки самого оптимізатора:

```text
OPTIMIZATION_GAIN =
  RAW_EXECUTION_TIME / OPTIMIZED_EXECUTION_TIME
```

Результати необхідно вимірювати на однаковому обладнанні, з однаковими вхідними даними та однаковими вимогами до коректності.

Вимірювання повинні враховувати прогрівання, варіативність часу та накладні витрати самого benchmark-інструмента.

# 19. Центральна дослідницька гіпотеза

Традиційне програмне виконання переважно орієнтоване на реалізацію алгоритму, визначеного програмістом.

SUBIT-CPU пропонує іншу перспективу:

**Обчислювальна задача повинна бути представлена так, щоб система могла аналізувати не лише те, що потрібно обчислити, а й те, як саме це обчислення найкраще організувати.**

Це змінює роль обчислювального ядра.

Воно перестає бути лише механізмом виконання операцій і стає системою аналізу та організації обчислювального процесу.

Основний цикл:

```text
UNDERSTAND
    ↓
REPRESENT
    ↓
ANALYZE
    ↓
OPTIMIZE
    ↓
EXECUTE
    ↓
VALIDATE
    ↓
LEARN FROM EXECUTION
```

Останній етап не означає автоматичного машинного навчання.

У v0.1 він означає накопичення вимірювань, профілів та результатів виконання, які можуть використовуватися для вдосконалення cost model і вибору стратегій у майбутніх версіях.
