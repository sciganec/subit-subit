# 0\. Мета специфікації

SUBIT-TECHNOLOGY-HISTOMAP v0.1 визначає архітектурні основи системи для дослідження технологічної історії людства як багатовимірного простору технологічних подій, контекстів, відносин, трансформацій і можливостей.

Специфікація визначає\:

1. Канонічну модель технологічних даних.
2. Онтологію технологічних подій.
3. Часову модель та історичну невизначеність.
4. Геометрію технологічної спіралі.
5. Модель технологічних зв'язків.
6. Архітектуру технологічних доменів.
7. SUBIT-64 контекстуальну проєкцію.
8. Принципи збереження історичної достовірності.
9. Механізми provenance та доказовості.
10. Архітектурні інваріанти.

## 0.1. Основний принцип

## DO NOT COLLAPSE — CONTEXTUALIZE

Технологічна подія не повинна бути зведена до одного року, одного винахідника, одного регіону, однієї категорії або одного причинного пояснення.

Кожна технологія існує в системі взаємопов'язаних історичних, матеріальних, інформаційних, соціальних, географічних і функціональних контекстів.

## 0.2. Архітектурна позиція

Система не повинна розглядати технологічну історію як\:

- лінійний прогрес;
- однозначну послідовність винаходів;
- історію лише видатних особистостей;
- історію лише західної цивілізації;
- рейтинг технологічної важливості;
- детерміновану послідовність, що неминуче приводить до сучасності.

Система повинна підтримувати множинність технологічних траєкторій, паралельні відкриття, незалежне виникнення, переривання, повторне використання, альтернативні архітектури та технологічні тупики.

# 3\. TEMPORAL MODEL — історичний час

## 3.1. Основна вимога

Час технологічної події не повинен бути представлений лише одним числом.

Історичні дані можуть мати різну точність\:

- точний день;
- точний рік;
- приблизний рік;
- інтервал років;
- століття;
- археологічний період;
- приблизний часовий діапазон;
- невизначене датування;
- декілька альтернативних датувань.

Система повинна зберігати саме той рівень точності, який підтримується джерелами.

# 4\. SPIRAL ENGINE — геометрична модель


## 4.1. Spiral as projection

Спіраль є геометричною проєкцією історичного часу, а не самою історією.

Для базової моделі\:

- t — історичний час;
- θ — кут;
- r — радіус;
- c — коефіцієнт масштабування;
- t₀ — базова точка;
- θ₀ — початковий кут.

Параметрична модель\:

θ(t) = θ₀ + 2π · (t − t₀) / P

де P — тривалість одного оберту в історичних роках.

Для базової конфігурації\:

P = 100 років.

Це означає, що один виток відповідає століттю.

## 4.2. Linear Spiral

Для лінійного радіального розміщення\:

r(t) = r₀ + a · &#124;t − t₀&#124;

де\:

- r₀ — початковий радіус;
- a — радіальний коефіцієнт;
- t — історичний час;
- t₀ — базовий часовий момент.

Тоді\:

x(t) = r(t) · cos(θ(t))

y(t) = r(t) · sin(θ(t))

Це забезпечує геометричну спіраль із фіксованим часовим періодом одного оберту.

Однак така модель має істотну проблему: технологічні події, що відбулися мільйони років тому, можуть потребувати непропорційно великого простору, тоді як сучасна історія, де кількість подій надзвичайно висока, візуально концентрується.

Тому Linear Spiral не може бути єдиним режимом.

## 4.3. Logarithmic Spiral

Для логарифмічної геометрії\:

r(t) = r₀ · exp(k · &#124;t − t₀&#124;)

Це дає можливість стиснути або розширити часовий простір, але має іншу властивість: історичні інтервали втрачають просторову лінійність.

Тому логарифмічна модель повинна бути режимом візуалізації, а не основним історичним координатором.

## 4.4. Canonical Time vs Visual Time

## DUAL-TIME ARCHITECTURE

---

**CANONICAL TIME**

Незмінний історичний час, який використовується в базі даних, розрахунках, пошуку та валідації.

---

**VISUAL TIME**

Просторове відображення історичного часу, яке може змінюватися відповідно до масштабу, геометрії та режиму дослідження.

Заборонено використовувати Visual Time для заміни або редагування Canonical Time.

## 4.5. Spiral Modes



**LINEAR SPIRAL**

Фіксований масштаб часу на виток.



**LOG SPIRAL**

Стиснення історичних масштабів.



**SEGMENTED SPIRAL**

Окремі масштабовані часові сегменти.



**MULTI-SPIRAL**

Паралельні технологічні траєкторії.

### Рекомендація для v0.1

Основний режим — SEGMENTED SPIRAL.

Він дозволяє поєднати\:

- реальний історичний масштаб;
- локальне збільшення щільних періодів;
- мільйонолітні часові інтервали;
- деталізацію сучасної історії;
- збереження порядку подій.

Геометрія повинна залишатися детермінованою: однакові дані, однакові параметри та однаковий режим завжди дають однакові координати.

# 5\. MULTI-SPIRAL DOMAIN MODEL

Технологічні домени не є взаємовиключними категоріями.

Одна технологія може належати до кількох доменів одночасно.

Наприклад, транзистор\:

- MATERIAL;
- ENERGY;
- INFORMATION;
- COMPUTATION;
- MANUFACTURING.

Тому доменне членство є множинним.

| ID | Домен | Опис |
|--------|--------|--------|
| MAT | MATERIAL | Матеріали, речовини, конструкції |

| INF | INFORMATION | Кодування, передача, зберігання |

| COM | COMMUNICATION | Комунікаційні системи |
| IND | INDUSTRY | Виробництво та промисловість |
| AGR | AGRICULTURE | Аграрні технології |

Доменний список повинен бути розширюваним.

Додавання нового домену не повинно змінювати базову модель технологічного вузла.

## 5.2. Domain intersections

Для кожного вузла система повинна підтримувати\:

- PRIMARY DOMAIN — основний домен, якщо його можна визначити;
- SECONDARY DOMAINS — додаткові домени;
- DOMAIN CONFIDENCE — обґрунтованість класифікації;
- DOMAIN PROVENANCE — джерело або метод класифікації.

Не кожна технологія має один очевидний основний домен.

У випадку неоднозначності допускається відсутність PRIMARY DOMAIN.

# 6\. TECHNOLOGY GRAPH ENGINE

## 6.1. Граф як окрема структура

Технологічний граф не є похідним від спіралі.

Спіраль і граф представляють два різні способи організації даних\:

- SPIRAL — історичне розташування;
- GRAPH — технологічні відносини.

Одна технологія може бути близькою до іншої за часом, але не мати прямого технологічного зв'язку.

І навпаки, дві технології можуть бути віддалені на тисячі років, але мати прямий структурний зв'язок.

## 6.2. Canonical Relation Types

## RELATION ONTOLOGY

---

PRECEDES

Хронологічне передування. Саме по собі не означає причинності.

---

ENABLES

Створює технологічні умови або можливості для іншої технології.

---

DEPENDS\_ON

Функціональна або конструктивна залежність.

---

DERIVED\_FROM

Вказує на реконструйоване походження або технологічне виведення.

---

INFLUENCES

Історичний, концептуальний або технологічний вплив.

---

TRANSFORMS

Змінює функцію, структуру або масштаб попередньої технології.

---

CONVERGES\_WITH

Поєднується з іншими траєкторіями в нову систему.

---

PARALLEL\_TO

Подібний розвиток без підтвердженої прямої залежності.

---

REUSES

Повторно використовує принцип, компонент або метод.

---

SUPERSEDES

Переходить на роль заміни попереднього технологічного рішення в конкретному контексті.

---

REVIVES

Повертає раніше відомий принцип у новий технологічний контекст.

## 6.3. Relation Object

```

{
  "id": "REL-000001",
  "source_id": "TECH-000001",
  "target_id": "TECH-000002",
  "relation_type": "ENABLES",
  "direction": "DIRECTED",
  "claim": "Technology A enabled a new class of Technology B.",
  "evidence_status": "SUPPORTED",
  "confidence": null,
  "sources": [],
  "context": [],
  "created_by": "EDITOR",
  "version": 1
}

```



`confidence: null` є навмисним.

Система не повинна генерувати фальшиву числову точність. Значення confidence додається лише тоді, коли існує визначена методологія його обчислення.

## 6.4. Graph integrity rules

- RELATION повинен посилатися на існуючі сутності.
- PRECEDES не є автоматично ENABLES.
- ENABLES не є автоматично CAUSES.
- PARALLEL\_TO не повинен створювати причинний ланцюг.
- DEPENDS\_ON повинен мати пояснення залежності.
- CONVERGES\_WITH повинен підтримувати множинні вхідні вузли.
- Один вузол може мати кілька альтернативних траєкторій.
- Цикли дозволені там, де вони відповідають реальним зворотним зв'язкам або рекурсивним технологічним процесам.
- Цикли, які виникають через помилки даних, повинні бути виявлені валідатором.

# 7\. TECHNOLOGY TRAJECTORY ENGINE

## 7.1. Траєкторія — не просто графовий шлях

TRAJECTORY — це окремий аналітичний об'єкт, який визначає, як система представляє певну історичну або концептуальну лінію розвитку.

Наприклад\:

`Mechanical Calculation → Programmable Mechanisms → Electromechanical Computation → Electronic Computing → Microprocessors → Modern Computing`

Це реконструйована траєкторія, а не твердження, що кожен етап був єдиною або безпосередньою причиною наступного.

## 7.2. Trajectory Types

- LINEAR — послідовна траєкторія;
- BRANCHING — траєкторія з розгалуженнями;
- CONVERGENT — зближення кількох напрямків;
- RECURSIVE — повторне використання принципів;
- CYCLIC — циклічні процеси;
- DISCONTINUOUS — переривання;
- RECONSTRUCTED — історично реконструйована траєкторія;
- HYPOTHETICAL — аналітична або гіпотетична траєкторія.

# 8\. SUBIT CONTEXT ENGINE

## 8.1. Призначення

SUBIT Context Engine додає до технологічної історії контекстуальну проєкцію.

Базова структура\:

WHO × WHERE × WHEN

64 стани.



Канонічні координати SUBIT\:

| Dimension | State | Code |
|--------|--------|--------|
| WHO | ME | 10 |
| WHO | WE | 11 |
| WHO | YOU | 01 |
| WHO | THEY | 00 |
| WHERE | EAST | 10 |
| WHERE | SOUTH | 11 |
| WHERE | WEST | 01 |
| WHERE | NORTH | 00 |
| WHEN | SPRING | 10 |
| WHEN | SUMMER | 11 |
| WHEN | AUTUMN | 01 |
| WHEN | WINTER | 00 |

Bit order\:

`WHO b1b2 + WHERE b3b4 + WHEN b5b6`

Code\:

`code6(s) = 32·b1 + 16·b2 + 8·b3 + 4·b4 + 2·b5 + b6`

## 8.2. SUBIT Context Projection

Технологічний вузол може мати\:

- один контекстуальний стан;
- кілька контекстуальних станів;
- змінний стан у часі;
- альтернативні контекстуальні інтерпретації;
- неповну проєкцію.

Наприклад, технологія може спочатку функціонувати як локальна індивідуальна практика, згодом стати колективною системою, а потім — глобальною інфраструктурою.

Ці переходи не повинні бути примусово зведені до одного коду.

## 8.3. Context Record

```

{
  "context_id": "CTX-000001",
  "entity_id": "TECH-000001",
  "subit64": {
    "who": null,
    "where": null,
    "when": null,
    "code6": null
  },
  "context_type": "HISTORICAL",
  "interpretation": "",
  "provenance": [],
  "status": "UNASSIGNED"
}

```



Цей запис демонструє структуру, а не готову класифікацію.

## 8.4. Context integrity

SUBIT-64 не замінює\:

- географічні координати;
- історичні календарі;
- культурні назви;
- цивілізаційні атрибуції;
- технологічні домени;
- типи зв'язків;
- джерела.

Він існує як окрема контекстуальна проєкція.

**Важлива межа**

WHO, WHERE і WHEN у SUBIT є координатами формальної моделі, а не автоматичними еквівалентами історичних категорій «винахідник», «країна» та «рік».

Переклад між історичними даними та SUBIT-координатами повинен бути окремою інтерпретаційною операцією з provenance.

# 9\. EVIDENCE ENGINE — джерела, достовірність та provenance

Evidence Engine є одним із критично важливих модулів системи.

Без нього Histomap ризикує стати красивою, але epistemically unreliable візуалізацією — картою, яка виглядає переконливо, але не дозволяє перевірити історичні твердження.

## 9.1. Claim-based evidence

Замість того щоб прив'язувати джерела тільки до TECHNOLOGY, система повинна прив'язувати джерела до конкретних тверджень.

Наприклад, технологія може мати різні історичні твердження\:

- винахід відбувся в певному році;
- технологія виникла в певному регіоні;
- конкретна особа пов'язана з її створенням;
- певний принцип був використаний у конструкції;
- технологія стала комерційно доступною в конкретний період.

Кожне твердження може мати різний рівень доказовості.

## 9.2. Claim Object

```

{
  "claim_id": "CLM-000001",
  "entity_id": "TECH-000001",
  "claim_type": "ORIGIN_DATE",
  "statement": "Technology emerged during the specified period.",
  "value": {
    "start": 1440,
    "end": 1455
  },
  "status": "SUPPORTED",
  "sources": [
    "SRC-000001"
  ],
  "review_status": "REVIEWED",
  "created_at": null,
  "updated_at": null
}

```



## 9.3. Claim statuses

| Статус | Значення |
|--------|--------|
| SUPPORTED | Підтверджується джерелами |
| PARTIALLY\_SUPPORTED | Підтверджено частково |
| DISPUTED | Існують суперечливі дані |
| UNVERIFIED | Не перевірено |
| REJECTED | Твердження відхилено |
| SUPERSEDED | Замінено новішою реконструкцією |

Статус не повинен визначатися просто кількістю джерел.

## 9.4. Provenance chain

Для кожного запису повинна бути можливість реконструювати\:

- хто створив запис;
- на основі яких джерел;
- коли він був створений;
- які зміни відбулися;
- хто змінив його;
- чому зміна була внесена;
- чи була зміна автоматично запропонована ШІ;
- чи перевірена вона людиною.

Модель provenance\:

`SOURCE → CLAIM → ENTITY → RELATION → TRAJECTORY → VISUALIZATION`

Таким чином, користувач може перейти від візуального вузла до конкретного історичного твердження та його доказової основи.

# 11\. VISUAL EXPLORATION ENGINE

## 11.1. Інтерфейс як інструмент дослідження

Система не повинна бути побудована за логікою традиційного каталогу.

Основний користувацький сценарій\:

1. Користувач відкриває глобальну спіраль.
2. Обирає історичний період.
3. Збільшує масштаб.
4. Виявляє технологічний кластер.
5. Відкриває технологічний вузол.
6. Переглядає його контекст.
7. Переходить до попередніх технологічних умов.
8. Відкриває GRAPH VIEW.
9. Простежує траєкторію.
10. Переходить до джерел.
11. Повертається до спіралі, зберігаючи поточний контекст.

Цей сценарій повинен бути базовим для UX-архітектури.

## 11.2. Navigation states

Система повинна зберігати\:

- поточний часовий діапазон;
- масштаб;
- центр візуалізації;
- вибраний вузол;
- активні домени;
- активні спіралі;
- тип графа;
- фільтри;
- SUBIT-контекст;
- історію навігації.

Це дозволяє переходити між режимами без втрати дослідницького контексту.

## 11.3. Technology Node Card

Картка технології повинна бути компактною, але мати можливість розширення.

# Technology Node

TECH-000001 · INFORMATION · COMPUTATION

## 11.4. Progressive disclosure

Інтерфейс не повинен одразу показувати всю інформацію.

Рівні розкриття\:

**L0 — SPIRAL NODE**

Назва, час, домен.

**L1 — QUICK VIEW**

Короткий опис, основний принцип, історичний контекст.

**L2 — TECHNOLOGY DETAIL**

Події, зв'язки, трансформації, домени.

**L3 — CONTEXT**

Географія, цивілізації, соціальні умови, SUBIT-64.

**L4 — EVIDENCE**

Джерела, твердження, provenance, дискусійні питання.

**L5 — SYSTEM ANALYSIS**

Технологічні траєкторії, графові залежності, конвергенції, відкриті можливості.

- цивілізації;

- матеріали;

- зв'язки;
- технологічні траєкторії;
- джерела.

## 12.2. Search modes

**ENTITY SEARCH**

Пошук конкретного винаходу, технології, події або системи.

**TEMPORAL SEARCH**

Пошук у заданому часовому діапазоні.

**DOMAIN SEARCH**

Пошук за технологічними доменами.

**RELATION SEARCH**

Пошук залежностей, впливів і технологічних зв'язків.

## 12.3. Exploratory queries

Система повинна дозволяти запити, які не прив'язані до конкретного вузла.

Наприклад\:

- Які технології змінили масштаб передачі інформації?
- Які винаходи незалежно виникли в різних цивілізаціях?
- Які технології з'явилися завдяки конвергенції енергетики та обчислення?
- Які технологічні принципи використовуються повторно через тисячоліття?
- Які технології виникли в один період, але мають різні траєкторії?
- Які технології спричинили найбільшу структурну трансформацію конкретної системи?
- Які сучасні технології мають найглибші історичні залежності?

У майбутньому такі запити можуть використовувати Natural Language Exploration, але результат повинен формуватися на основі канонічних даних і графових структур.

Кожна гіпотеза повинна мати статус і відокремлене походження.

# 14\. DATA VALIDATION ENGINE

Валідація повинна відбуватися на кількох рівнях.

## 14.1. Schema Validation

Перевіряє\:

- структуру запису;
- типи полів;
- допустимі значення;
- обов'язкові поля;
- формат ідентифікаторів;
- версії схем;
- типи часових даних.

## 14.2. Referential Integrity

Перевіряє\:

- існування referenced IDs;
- коректність зв'язків;
- відсутність dangling references;
- валідність технологічних залежностей;
- відповідність типів сутностей.

## 14.3. Temporal Integrity

Перевіряє\:

- коректність початкової та кінцевої дат;
- логічність часових інтервалів;
- сумісність дат подій і технологій;
- правильне відображення BCE/CE;
- відсутність випадкової зміни історичного часу при перемиканні режимів спіралі.

## 14.4. Graph Integrity

Перевіряє\:

- допустимість типів зв'язків;
- напрямок;
- існування вузлів;
- логічні конфлікти;
- цикли;
- дублікати;
- суперечливі відношення.

## 14.5. Evidence Integrity

Перевіряє\:

- чи існують джерела;
- чи прив'язані вони до тверджень;
- чи не використовуються невалідні URL;
- чи відокремлені первинні та вторинні джерела;
- чи не представлені неперевірені твердження як підтверджені.

## 14.6. Context Integrity

Перевіряє\:

- валідність SUBIT-64;
- відповідність бітового порядку;
- правильність code6;
- наявність provenance контекстуального призначення;
- відсутність неприпустимого зведення історичних даних до контекстуального коду.

# 15\. TESTING ARCHITECTURE

Тестування повинно починатися до створення повної історичної бази.

## 15.1. Geometry Tests

- однакова дата дає однакові координати при незмінних параметрах;
- зміна масштабу не змінює історичні дані;
- координати залишаються в межах допустимого простору;
- масштабування зберігає порядок історичних подій;
- сегментовані переходи не створюють часових колізій;
- обчислення не породжують NaN або Infinity;
- геометрія коректно працює з негативними історичними датами.

## 15.2. Data Tests

- кожен запис має унікальний ID;
- усі referenced IDs існують;
- домени валідні;
- типи сутностей коректні;
- temporal ranges валідні;
- джерела правильно пов'язані;
- записи підтримують версіонування.

## 15.3. SUBIT Tests

Для всіх 64 станів\:

- код повинен бути в діапазоні 0–63;
- кодування має бути однозначним;
- декодування повинно повертати первинний стан;
- усі 64 стани повинні бути представлені;
- не повинно бути дублікатів кодів.

## 15.4. Graph Tests

- зв'язок не може посилатися на неіснуючий вузол;
- directed relations зберігають напрямок;
- паралельні траєкторії не перетворюються на причинні;
- графові цикли не призводять до нескінченної навігації;
- пошук шляхів має обмеження глибини;
- графова навігація не повинна блокувати інтерфейс.

## 15.5. Visual Tests

- читабельність при різних масштабах;
- доступність вузлів;
- відсутність неконтрольованого накладання;
- правильне відображення кластерів;
- стабільність позицій;

# 18\. Важливе архітектурне рішення: не починати з 4823 записів

Technology Histomap привертає увагу великою кількістю подій.

Але для SUBIT я б не ставив 4823, 10 000 або 100 000 записів як стартову мету.

Перший етап повинен довести три речі\:

**A. GEOMETRY**

Чи можна зручно досліджувати історію через спіраль?

**B. CONTEXT**

Чи можна перейти від технологічного вузла до його контексту, не втрачаючи структуру?

**C. RELATIONS**

Чи може користувач досліджувати технологічну історію через зв'язки, а не тільки через хронологію?

Якщо ці три принципи працюють на 100–300 добре сформованих технологічних вузлах, тоді масштабування даних буде логічним наступним етапом.

Якщо ж вони не працюють на малому наборі даних, десятки тисяч записів лише збільшать складність.
